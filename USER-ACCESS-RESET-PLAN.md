# User access reset from the Admin Users table

Status: **implemented through phase 3, root gate green, published** (2026-09-20).
The phase 1–3 slice is committed and pushed — Kafil `e40a3e5` on `main`, najm
`e742184` on `master`, both matching upstream. Phase 4's connected/browser
acceptance and deployment are **not** done and are not claimed. A later review
found two behaviour gaps; both are fixed, and the Najm half is released as
`najm-auth@4.0.8`. Evidence, including what is still owed, is in
`docs/evidence/user-access-reset/README.md`.

## Goal and product contract

Add one **Reset access** action to each eligible row of the admin-only `/users` table. The action opens a confirmation dialog explaining the exact consequence for that account. The client sends the selected user ID, an administrative reason, and `expectedMode` for the consequence shown in the dialog. The backend chooses the workflow from the current account state and linked profile and refuses a mismatched confirmation; `expectedMode` never selects the workflow. Do not make the existing password visible or add a generic password-edit field.

| Current account | Server-selected result | User's next step |
| --- | --- | --- |
| Active family with a valid linked family profile | Replace the credential with the guardian's normalized CIN, require Najm password setup, revoke all sessions | Sign in with email + CIN, complete `/change-password`, then sign in again |
| Active operator or delivery staff with a valid linked staff profile | Send a one-time password-reset email to the account's current address | Follow the link, set a new password, sign in again |
| Active sponsor with a valid linked sponsor profile | Send the same one-time reset email | Follow the link, set a new password, sign in again |
| Pending, invited staff or sponsor account with its linked profile | **Resend invitation**, not an ordinary reset | Follow the invite link, set a password, activate the account |
| Inactive, bootstrap admin, self-target, unknown role, unlinked profile, or pending applicant identity | No reset; explain why or return a safe conflict | Use the existing authorized lifecycle or applicant workflow |

“Staff” is a Kafil profile, not a role: operator and delivery are the applicable auth roles. The single action must work in desktop table and mobile card modes. The confirmation copy must distinguish **reset to CIN**, **email reset**, and **resend invitation**; it must never print the CIN, a password, a token, or an invite URL.

Scope excludes changing a user's email, changing the guardian CIN, editing the admin's own/bootstrap credentials, auto-reactivating accounts, approving applicants, sending credentials in clear text, and giving operators access to this admin-only command. Existing password-change and public forgot-password flows remain intact.

## Verified starting point and implementation gates

- `/users` requires `admin`; `AdminUsersPage` currently offers View, Deactivate/Reactivate, and Revoke Sessions, with no reset action. Kafil owns these UI files under `apps/web/src/features/AdminAccess/` and the API client in `apps/web/src/services/adminAccessApi.ts`.
- `AdminAccessController` has explicit admin-guarded commands; `AdminAccessService.ensureSafeTarget()` already blocks self and bootstrap-admin targets. Extend that same boundary, not a generic Najm user-update route.
- New family provisioning already uses `moroccanCinTemporaryCredential(guardianCin)` with `requireCredentialSetup: "password"`; the family profile stores the CIN and can be looked up by `userId`. Keep the lookup server-only and project no CIN into the Admin Users response.
- Najm Auth installed through root `overrides` is currently `4.0.6`. It has one-time reset/invite tokens, public `/auth/reset-password`, purpose-bound credential setup, and session revocation. However, `AuthService.forgotPassword(email)` returns a generic success even if sending fails; `AuthService.inviteUser()` creates a **new** user, not a re-invitation; and `UserService.update({ password })` applies normal password-strength validation. **None is a verified existing-user reset-to-CIN command.** Do not compose these APIs naively and claim the new workflows are safe.
- Sponsor applicants are separate from approved sponsor profiles. A pending applicant identity must not be converted into an approved sponsor by a Users-table reset.
- Before implementation, re-read root `AGENTS.md`, the applicable frontend/backend/browser skills, `docs/plans/README.md`, the current installed declarations, and the relevant Next.js 16 docs for any route or client/server changes. Inspect the exact E2E runner/spec before adding browser assertions. Preserve existing dirty work, including unrelated E2E edits.

## Phase 1 — settle and test the shared Najm auth contracts

1. In the sibling Najm Auth package, confirm whether a newer installed/published release already provides the three existing-account operations below. If not, implement them in Najm Auth rather than duplicating hashing, token templates, or setup/session logic in Kafil. Review the exact source and public declarations before choosing method names.
2. Provide an explicit **reset existing account to temporary credential** operation. It must validate the temporary credential kind (`ma-cin`), normalize and hash the CIN using Najm's existing helper, write the new hash and durable `password` setup requirement as one atomic database operation, and invalidate/revoke every normal session. It must not use normal permanent-password strength validation or issue a normal session. A failed write must not leave the CIN usable without a setup requirement or leave the old password unexpectedly replaced. Test transaction rollback, concurrent requests, repeat reset, old-password denial, CIN login's `credential_setup` result, and completion/replay behavior. Verify cache/session invalidation failures fail closed and are not silently reported as success.
3. Provide an **admin-initiated, user-ID-bound reset-email** operation for an existing active account. It should send to the email read from that same account at command time, use Najm's normal single-use reset token/template, preserve account status and email-verification state, and distinguish accepted delivery from failure. Do not call an email-address-only public forgot-password endpoint and assume delivery succeeded. Decide whether delivery failure invalidates a newly minted token or allows an existing link to remain valid; test that behavior explicitly. Avoid logging token, link, body, or credentials.
4. Provide a **resend invitation for an existing pending invited account** operation. It must not create a second user or second profile; use Najm's invite token/template and existing activation semantics. Reject active/inactive accounts. Confirm that an invite activates only a pending invited account, not a sponsor application awaiting approval. Repeated sends should supersede earlier links in the documented token contract. Return a truthful delivery result.
5. Ensure the package API is narrow enough that Kafil can enforce admin authorization, target eligibility, rate limits, reason, and audit. Add package unit/integration tests for token single-use, expiry/supersession, recipient binding, status preservation, session revocation, failure modes, and four-locale template behavior where applicable. If a DB/schema change is required, generate a new migration; never alter a deployed one.
6. Publish a versioned Najm Auth release only after its package gates pass. Verify the registry artifact is available, then update Kafil's root override/lockfile, reinstall with Bun, and verify the installed `.d.ts` and runtime exports. Record package/source/registry/consumer evidence separately. Do not build Kafil against a sibling checkout while claiming the published artifact works.

**Stop condition:** do not proceed with the family or pending-account UI path unless the installed Najm contract can provide the atomic temporary reset and existing-account re-invite behavior. If a safe shared implementation is impossible within the slice, report that dependency instead of using direct SQL, `UserService.update({ password: CIN })`, `inviteUser()` on an existing account, or an ad hoc email template.

## Phase 2 — Kafil server command and policy

1. Add `POST /api/admin/access/users/:userId/reset-access` to `AdminAccessController` with `@isAdmin()` and validated params/body (`reason`: trimmed, 3–500 characters; optional `expectedMode` confirmation). Resolve the actor with Najm's authenticated principal. Do not expose this sensitive command as an MCP tool by default; if MCP exposure is separately authorized, require destructive/confirmation metadata and denial tests. Keep one endpoint and one response discriminant such as `mode: "family_credential_setup" | "reset_email_sent" | "invitation_resent"`; never return the CIN, token, or email contents.
2. In `AdminAccessService`, reload the target and profile state at execution time. Reuse `ensureSafeTarget`; allow only `status === "active"` for family and reset-email branches or `status === "pending"` for a verified invited-account branch. Reject inactive users, applicant-only identities, unsupported roles, mismatched role/profile links, absent email, and stale UI assumptions. Compare a supplied `expectedMode` to the server-selected mode and refuse a mismatch; never trust it to select a workflow. Do not trust client-provided role, email, CIN, or status.
3. For family reset, read the guardian CIN through a narrow server-side repository query tied to the target `userId`, validate/normalize it with Najm's Moroccan identity helper, and pass it only to the shared temporary-credential command. Never include it in an API response, audit/outbox metadata, notification, error, or log. Confirm whether the existing family CIN can have a shape the helper rejects and return a safe conflict without partial mutation.
4. For active staff/sponsor and eligible pending invited users, call the shared Najm email commands using the exact target user ID. A `200` must mean the declared action really completed; if mail delivery is unavailable or failed, return an explicit failure or truthful `email_not_sent` result and show it in the UI. The current console/memory email provider must not be mistaken for real delivery. Do not change lifecycle status merely to enable sending.
5. Add an audit event with actor ID, target ID, reason, selected mode, and a value-free delivery outcome. Do not audit the CIN, raw email body, password, token, reset URL, or sensitive family data. Set deliberate rate limits/cooldowns for repeat administrative sends and test parallel clicks; use Najm rate facilities or an existing Kafil pattern, not a client-only throttle. Any irreversible email/token operation should be ordered with audit and transaction boundaries so partial failures are explicit and recoverable.
6. Preserve existing revoke-sessions semantics. Reset-to-CIN must revoke before the user can establish a new normal session; password reset and accepted invitation must revoke all previous sessions via Najm. A reset-email *request* alone should not revoke a user's working session unless the reviewed Najm contract intentionally does so; the actual password change must revoke it. Specify this timing in tests and UI copy.
7. Update `packages/server/test/admin-access-modules.test.ts` and focused real-PostgreSQL tests for allowed and denied modes, self/bootstrap admin, applicant/inactive/unlinked targets, delivery failures, concurrent requests, rollback, audit privacy, session invalidation, and MCP discovery. If a new policy capability is introduced, update controller policy, seed definitions/grants, seed verification, and denial tests together. Prefer the existing `@isAdmin()` boundary if no new capability is needed.

Keep it one action, not a staff/sponsor/family menu fork. Disable or omit it for known admin/inactive/ineligible rows as presentation only; backend validation remains authoritative.

## Release, rollback, and evidence boundaries

- **Source complete** means code plus focused tests and root gate pass. **Package complete** requires a published/installable Najm artifact and verified Kafil override. **Database complete** requires any generated migration and real-DB tests. **Git publication** requires clean intended commits and matching local/upstream HEAD. **Deployment** requires the exact healthy running revision. **Connected/browser acceptance** requires the actual journeys above. Do not collapse these verdicts.
- Deploy Najm-compatible Kafil only after the required package exists and any migration is applied. Verify email transport configuration without printing secrets; a webhook response or image build alone is not proof of deployment. Production reset execution and remote mailbox tests require a separate, explicitly authorized operations/acceptance step.
- Rollback before any reset command: revert/disable the Kafil UI and endpoint and restore the prior compatible package pin if necessary. Rollback after a family reset cannot recover the old password or un-revoke sessions; the affected family must finish setup or use a newly reviewed recovery action. A sent reset/invite link remains subject to Najm's expiry/one-time semantics; disabling the admin button does not unsend mail. Preserve audit history. Do not use a database restore to “undo” a single credential action.
- Keep a sanitized evidence record under `docs/evidence/user-access-reset/` when implementation begins: package artifact/version, Kafil commit, schema/migration decision, tests, local connected results, deployment revision (if any), and explicit remaining work. Do not put secrets or generated credentials in the plan or evidence.
