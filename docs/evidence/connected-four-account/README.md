## Test defects corrected in this slice

Each correction was confined to `apps/web/test/e2e/connected-four-account.e2e.ts`.
No Kafil feature code, Najm package, migration, schema column, dependency, or
production route was changed.

1. **Phone input clears the dial-code prefix when the textbox is `Ctrl+A`/`Delete`**
   then re-typed. react-international-phone pre-fills `+212 ` in the textbox, but
   clearing it strips the dial code from internal state. The fix is to click at
   the end of the field (`phoneTextbox.press("End")`) and type the local part
   without clearing. The PhoneInput's per-keystroke `onChange` then fires with
   the full international value, and the rendered input value matches the
   expected E.164 after stripping the formatter's spaces/dashes. The DB row
   stores the expected E.164 (the value is `[MASKED E.164]` in this report).

2. **Two `console.log` calls leaked the generated phone** in
   `[c4a] phone initial inputValue=…` and `[c4a] phone after type inputValue=…`.
   Removed both. The phone value is no longer written to stdout, the
   Playwright log file, the `test-results/.../error-context.md`, or any
   evidence file.

3. **Required-field `formLabel` rendering includes the trailing `*` in the
   textbox accessible name.** `getByLabel("Full name", { exact: true })`
   resolves to zero elements. Replaced with
   `getByRole("textbox", { name: "Full name *" })` for the applicant form's
   `Full name`, `Email address`, and `Password` inputs. The login form's
   `Email or phone`/`Password` accessible name does NOT include the `*`, so it
   is matched with substring `getByLabel("Email or phone")`.

4. **`expectExactNegativeResponse` did not return the response object**, so the
   body of the denied POST `/api/auth/login` could not be inspected. Updated the
   helper to return `{ result, response }` and updated both work-unit-C callers
   to destructure the new shape.

5. **Approve replay must hit the network, not the row context menu.** The
   earlier "menu-item absence" assertion is only UI proof; the plan asked for a
   real `POST /api/applicants/{id}/approve` replay. The replay now uses the
   admin session cookies to call the endpoint directly and asserts a 409 whose
   body matches the regex `/pending review|already/i` (regex match, not exact
   equality — the body is `Only pending review or rejected applications can be
   approved`).

6. **Independent queries for users and sponsor profiles.** The earlier lookup
   joined both tables in a single statement, which obscured whether one side
   had duplicated. Replaced with two independent `SELECT … FROM users` /
   `SELECT … FROM sponsor_profiles` queries. `users.status = 'active'` is
   asserted only on the user row; `sponsor_profiles` has no `status` column
   and is verified by the link to that user plus the phone value.

7. **Diagnostics console-error filter is now per-status, separately counted.**
   The previous filter allowed any console error whose status matched ANY
   registered `expectedResponses` entry, which could silently hide an
   unrelated later 4xx. The diagnostics object now has a separate
   `expectedConsoleErrors: { status, count, consumed }[]` list. Each expected
   negative response (status ≥ 400) registers exactly one console-error
   allowance with `count = 1`. The console listener decrements the count once
   for the matching `Failed to load resource: status of NNN` text. At the end
   of the test, `assertDiagnosticsClean` verifies every allowance has
   `count === 1 && consumed === count`. An unrelated later 4xx of the same
   status would not be hidden because no allowance would be open.

8. **Diagnostics failed-request filter for Next.js static chunks.** When the
   admin page closed before its `_next/static/chunks/*` requests finished, those
   `net::ERR_ABORTED` cancellations were recorded as failed requests.
   Filtered the listener to ignore genuine navigation-cancellation failures.

9. **`/api/sponsors/me/profile` 401 after logout** is now registered via
   `registerExpectedResponse(...)` before the `fetch` is issued, so both the
   response-listener and the console-listener consume it instead of recording
   it as unexplained 4xx output.
